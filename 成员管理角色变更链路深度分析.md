# Plausible Analytics 成员管理角色变更链路深度分析

## 一、角色变更的两个独立场景

Plausible 实现了**两套独立的角色变更机制**，分别用于不同的管理场景：

| 场景 | 入口位置 | 管理对象 | 可变更角色范围 |
|------|----------|----------|----------------|
| **站点访客成员管理** | Site Settings → People | `guest_membership`（访客成员关系） | **仅限** `:editor` ↔ `:viewer` |
| **团队成员管理** | Team Settings → Team Management | `team_membership`（团队成员关系） | 所有角色（含 `:admin`, `:owner` 等），但有复杂约束 |

## 二、场景一：站点访客成员管理（Site Settings → People）

### 2.1 入口与管理范围

- 前端模板：`lib/plausible_web/templates/site/settings_people.html.heex`

### 2.3 控制器层拦截

**文件位置**：`lib/plausible_web/controllers/site/membership_controller.ex:18-21`

```elixir
defmodule PlausibleWeb.Site.MembershipController do
  @moduledoc """
    This controller deals with user management via the UI in Site Settings -> People. 
    It's important to enforce permissions in this controller.

    Owner and Admin - Can manage users, can trigger a 'transfer ownership' request
    Editor and Viewer - Can not access user management settings
    Anyone - Can accept invitations

    Everything else should be explicitly disallowed.
  """

  plug PlausibleWeb.RequireAccountPlug
  
  # ================================================
  # 接口层强制校验：仅 owner 和 admin 可访问此控制器
  # ================================================
  plug PlausibleWeb.Plugs.AuthorizeSiteAccess, [:owner, :admin]
```

**接口层拦截规则**：
| 操作者角色 | 是否允许访问 |
|------------|--------------|
| `:owner` | ✅ 允许 |
| `:admin` | ✅ 允许 |
| `:editor` | ❌ 404 Not Found |
| `:viewer` | ❌ 404 Not Found |

> 注意：权限不足时返回 **404 Not Found**（模糊错误，不暴露权限细节）

### 2.4 业务层权限校验

**文件位置**：`lib/plausible/teams/memberships.ex:130-157`

```elixir
def update_role(site, user_id, new_role_str, current_user, current_user_role) do
  new_role = String.to_existing_atom(new_role_str)
  
  # ================================================
  # 关键点1：只处理 guest_membership（访客成员关系）
  # 非访客成员会返回 {:error, :no_guest}
  # ================================================
  case get_guest_membership(site.id, user_id) do
    {:ok, guest_membership} ->
      
      # ================================================
      # 关键点2：不能修改自己的角色
      # ================================================
      can_grant_role? =
        if guest_membership.team_membership.user_id == current_user.id do
          false  # 目标是自己 → 拒绝
        else
          # ================================================
          # 关键点3：检查角色授予规则
          # ================================================
          can_grant_role_to_other?(current_user_role, new_role)
        end
      
      if can_grant_role? do
        guest_membership =
          guest_membership
          |> Ecto.Changeset.change(role: new_role)
          |> Repo.update!()
          |> Repo.preload(team_membership: :user)
        
        {:ok, guest_membership}
      else
        {:error, :not_allowed}
      end
    
    {:error, _} ->
      {:error, :no_guest}  # 非访客成员 → 拒绝
  end
end
```

### 2.5 角色授予规则（核心）

**文件位置**：`lib/plausible/teams/memberships.ex:179-183`

```elixir

defp can_grant_role_to_other?(:owner, :viewer), do: true
defp can_grant_role_to_other?(:admin, :editor), do: true
defp can_grant_role_to_other?(:admin, :viewer), do: true
```

**整理成表格**：

| 操作者角色 | 可授予的目标角色 | 不可授予的角色 |
|------------|------------------|----------------|
| `:owner` | `:editor`, `:viewer` | `:owner`, `:admin`, `:billing`, `:guest` |
| `:admin` | `:editor`, `:viewer` | `:owner`, `:admin`, `:billing`, `:guest` |
| `:editor` | 无（所有情况都返回 false） | 所有 |
| `:viewer` | 无（所有情况都返回 false） | 所有 |

### 3.3 业务层核心逻辑

**文件位置**：`lib/plausible/teams/memberships/update_role.ex:12-49`

```elixir
def update(team, user_id, new_role_str, current_user) do
  new_role = String.to_existing_atom(new_role_str)
  
  with :ok <- check_valid_role(new_role),                                       # 检查1
       {:ok, team_membership} <- Memberships.get_team_membership(team, user_id), # 检查2
       {:ok, current_user_role} <- Memberships.team_role(team, current_user),    # 检查3
       granting_to_self? = team_membership.user_id == current_user.id,            # 检查4
       :ok <-
         check_can_grant_role(
           current_user_role,
           team_membership.role,
           new_role,
           granting_to_self?
         ),                                                                          # 检查5
       :ok <- check_owner_can_get_demoted(team, team_membership.role, new_role), # 检查6
       team_membership = Repo.preload(team_membership, :user),
       :ok <- check_can_promote_to_owner(team, team_membership.user, new_role)   # 检查7
  do
    # 执行角色变更
    ...
  end
end
```

### 3.4 七项关键检查

#### 检查 1：目标角色有效性

```elixir
defp check_valid_role(role) do
  if role in (Teams.Membership.roles() -- [:guest]) do
    :ok
  else
    {:error, :invalid_role}
  end
end
```

**规则**：目标角色不能是 `:guest`

| 目标角色 | 是否有效 |
|----------|----------|
| `:owner` | ✅ |
| `:admin` | ✅ |
| `:editor` | ✅ |
| `:viewer` | ✅ |
| `:billing` | ✅ |
| `:guest` | ❌ `{:error, :invalid_role}` |

#### 检查 2：目标用户存在

调用 `Memberships.get_team_membership(team, user_id)` 检查目标用户是否是团队成员。

#### 检查 3：获取操作者角色

调用 `Memberships.team_role(team, current_user)` 获取操作者在团队中的真实角色。

#### 检查 4：判断是否在修改自己

`granting_to_self? = team_membership.user_id == current_user.id`

#### 检查 5：角色授予规则（核心）

**文件位置**：`lib/plausible/teams/memberships/update_role.ex:92-131`

```elixir
# 分支 A：修改自己的角色
defp check_can_grant_role(user_role, _from_role, to_role, true) do
  if can_grant_role_to_self?(user_role, to_role) do
    :ok
  else
    {:error, :permission_denied}
  end
end

# 分支 B：修改他人的角色
defp check_can_grant_role(user_role, from_role, to_role, false) do
  if can_grant_role_to_other?(user_role, from_role, to_role) do
    :ok
  else
    {:error, :permission_denied}
  end
end
```

| 操作者当前角色 | 可降级到的角色 | 不可变更 |

| `:viewer` | 无 | 所有变更都拒绝 |
| `:billing` | 无 | 所有变更都拒绝 |

## 五、两套管理机制的对比总结

### 5.1 核心差异

| 维度 | 站点访客管理（Site Settings → People） | 团队成员管理（Team Settings → Team Management） |
|------|----------------------------------------|------------------------------------------------|
| **管理对象** | `guest_membership`（访客成员关系） | `team_membership`（团队成员关系） |
| **可变更角色** | 仅限 `:editor` ↔ `:viewer` | 所有角色（`:owner`, `:admin`, `:editor`, `:viewer`, `:billing`） |
| **前端 Admin 路径** | ❌ 不存在 | ✅ 存在 |
| **Owner 变更约束** | 前端 disabled，后端实际不处理（Owner 不是访客） | 需满足"至少一个 Owner"约束 |
| **角色授予规则** | 简单 4 条规则 | 复杂的"修改自己"和"修改他人"分支规则 |
| **适用场景** | 外部合作方、临时访问者 | 团队内部成员 |

### 5.2 可操作的角色变更范围汇总

#### 场景一：站点访客管理

| 操作者 | 可变更的目标角色 | 不可变更 |
|--------|------------------|----------|
| `:owner` | `:editor` → `:viewer`, `:viewer` → `:editor` | 所有其他角色（包括 `:admin`） |
| `:admin` | `:editor` → `:viewer`, `:viewer` → `:editor` | 所有其他角色（包括 `:admin`） |
| `:editor` | 无（接口层拦截） | 所有 |
| `:viewer` | 无（接口层拦截） | 所有 |

**关键**：此场景**没有 Admin 变更路径**，前端和后端都不支持。

#### 场景二：团队成员管理

##### 修改自己的角色

| 操作者当前角色 | 可变更到 | 不可变更 |
|----------------|----------|----------|
| `:owner` | `:admin`, `:editor`, `:viewer`, `:billing` | `:owner`（已是最高） |
| `:admin` | `:editor`, `:viewer`, `:billing` | `:owner` |
| 其他角色 | 无 | 所有 |

##### 修改他人的角色

| 操作者 | 目标当前角色 | 可变更到的目标角色 |
|--------|--------------|--------------------|
| `:owner` | 任意角色 | 任意角色（无限制） |
| `:admin` | `:admin` | `:admin`, `:editor`, `:viewer`, `:billing` |
| `:admin` | `:editor` | `:admin`, `:editor`, `:viewer`, `:billing` |
| `:admin` | `:viewer` | `:admin`, `:editor`, `:viewer`, `:billing` |
| `:admin` | `:billing` | `:billing`（只能保留） |
| `:admin` | `:owner` | 无（不能修改 Owner） |
| `:admin` | `:guest` | 无（不能修改 Guest） |
| 非 owner/admin | 任意 | 无（接口层拦截） |

### 5.3 关键安全设计

1. **模糊错误信息**：
   - 权限不足时返回 `404 Not Found`，而不是 `403 Forbidden`
   - 避免暴露系统内部权限结构

2. **不依赖前端传递**：
   - 操作者角色从数据库查询，不使用前端传递的参数
   - 防止前端篡改

3. **多层校验**：
   - 前端展示层（体验优化）
   - 接口层（强制校验）
   - 业务层（深度校验）

4. **Owner 特殊保护**：
   - 团队必须至少有一个 Owner
   - Admin 不能修改 Owner 的角色
